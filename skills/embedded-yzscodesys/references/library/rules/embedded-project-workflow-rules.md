# 嵌入式工程前提、审核与实施流程

日期：2026-10-27。状态：用户已明确要求的工程流程，配套字段和证据形式为工程适配说明。

[返回框架总规则](../embedded-framework-rules.md) · [资料与逐步审核表模板](../templates/embedded-project-review-tables.md)

本文件适用于新建、重构和芯片移植工程。先按本流程收集资料、分析并审核，再按总规则和专项细则实现。当前整理本规范不等于已经取得某个具体工程的芯片资料、审核结论、构建或硬件验证结果。

## 1. 总体流程与执行状态

流程为：资料收集 → 芯片/工具链/原理图及旧代码分析 → 裸机或 FreeRTOS 方案 → HTML 框架、引脚与逻辑/波形审核 → 用户逐步确认 → IDE 工程搭建与实现 → 规范三轮复盘 → 逻辑和引脚三轮复盘 → IDE 构建与优化风险处理 → 接线就绪后的自动烧录 → 调试观察与交付。

| 状态 | 含义 |
| --- | --- |
| 待提供 | 缺少资料，记录具体缺项，不填入猜测值 |
| 已分析/待审核 | 已有方案和依据，尚未获得用户确认 |
| 已确认 | 用户明确确认了所列版本、审核项和适用范围 |
| 需修改 | 用户反馈或检查发现问题，修正受影响项后复核 |
| 已验证 | 有本次对应检查、构建或硬件证据；同时写明验证层级 |
| 需手工处理 | 自动执行无法继续，列出原因、原始错误和最小手工操作 |
| 不适用 | 写明对象和理由，不把未检查或资料缺失记为不适用 |

未提供的资料先列入缺项，继续不依赖它的分析。只在依赖这些资料的决定上等待；不得以猜测的引脚、电平或时序搭建已确认工程。

## 2. WF01–WF03：用户资料与平台识别

首先请用户提供以下材料。已有资料直接复用，不重复询问；关键资料缺失时明确其影响。

| 输入 | 用户提供的内容 | 分析与记录要求 |
| --- | --- | --- |
| 芯片型号 | 厂商、完整订货型号、封装；可提供丝印、开发板/模组型号及硬件版本 | 记录中国厂商或其他厂商分类，并单独识别 ESP 系列及其 SDK 生态；核对 CPU 架构、实际内存和外设资源，不能只凭厂商地域判断工具链 |
| 芯片规格书 | 对应具体型号/封装的规格书；已有参考手册、勘误表一并提供 | 保存文件、版本和页码/章节，作为寄存器、引脚、时钟、电气和底层行为的核对依据 |
| IDE 环境 | CCS、Keil 或 VS Code，安装路径、版本、编译器与调试器；已有工程配置 | 明确编译器、器件支持包、SDK、链接配置、ABI 和优化级别；VS Code 的编辑环境与实际编译/烧录工具链分别记录 |
| 工作类型 | 新建、重构或移植；目标功能、原行为保持范围 | 新建从需求确定方案；重构/移植按第3节读取已有工程 |
| 原代码路径 | 重构/移植时提供源码和已有工程路径 | 读取实际源码、构建配置和相关文档，不仅看目录名字 |
| 芯片例程或 lib 包 | 用户持有的对应型号官方例程、SDK、库和版本 | 缺少时按第5节上网寻找，核对适用型号和工具链 |
| 工程原理图 | 原生 EDA 文件，或可辨识的 PDF/图片；已有网表、BOM、板卡版本 | 建立物理引脚、GPIO/外设、网络和外围电路之间的映射 |
| 烧录与调试连接 | 当前板卡、探针/下载器、端口和接线状态 | 可在资料阶段登记，实际烧录与调试前重新核对当前连接和目标 |

ESP 系列与中国厂商分类可能重叠，按“厂商属性 + 具体芯片 + SDK/工具生态”分别记录。不把中国厂商芯片等同于 STM32，也不根据相似名称套用寄存器、启动文件、引脚或库。

工程涉及UI设计或优化时，追加屏幕尺寸/分辨率、驱动芯片及现有UI资料，按[UI规范](embedded-ui-rules.md)核对8项Skill，输出3–4套HTML风格供审核；这一条件分支不要求无UI工程收集屏幕。

按用户提供的规格书检索并核对底层问题。必要时补充厂商官方参考手册、勘误、SDK 文档和示例；记录来源和版本，冲突项列出待核实。不能用另一子型号或封装的资料代替当前型号。

IDE 选择应验证该型号的实际支持情况。用户提供的 IDE 与芯片/编译器不匹配时，先呈现差异和可行环境供确认，不自行换成另一套环境后宣称满足要求。

## 3. WF04：重构与移植的原工程分析

用户提供旧代码路径后，先只读分析：

1. 确定工程根目录、目标 MCU、启动/向量、时钟、链接文件、编译组合、SDK 和第三方边界。
2. 读取 main、任务调度、中断、驱动、业务模块和通信/持久化入口，画出实际依赖与数据所有权。
3. 判断现有系统是裸机、FreeRTOS、其他 RTOS，还是混合调度；记录证据，不能仅凭文件夹名称判断。
4. 核对代码引脚、原理图、规格书、现有时序和保护行为，登记冲突与未验证项。
5. 保存基线摘要、已知问题、现有构建/测试事实及行为保持范围，提出保留、重构和迁移边界。
6. 分析进入框架方案阶段后，输出第7节的 HTML 和逐步审核表，等待用户确认后再搭建或改造工程。

审核前可继续读源码、查资料、分析和编制方案；不覆盖旧代码、不执行批量重命名、不迁移调度内核、不烧录。旧工程的历史授权和通过记录不替代本次方案确认。

## 4. WF05：裸机分时处理或 FreeRTOS 框架

保持 `Task → APP → FML → HDL` 的职责方向；系统调度方式单独适配。

| 分支 | 输出的系统框架 | 必须说明 |
| --- | --- | --- |
| 裸机 | 基于时基的分时处理框架 | 启动顺序、主循环、周期/事件任务表、非阻塞状态机、中断与前台边界、运行预算、超时/计时回绕和超期处理 |
| RTOS | FreeRTOS 框架 | 内核/移植版本、任务周期与优先级、栈及堆策略、队列/通知/同步、ISR 允许接口、错误恢复和资源预算 |

裸机分时处理不能靠长时间 delay 串行阻塞各功能；时间敏感的采样、控制和保护按真实硬件要求保留在中断或专用外设中，不强行搬到普通周期任务。

重构工程先识别原系统，再选择对应输出。原工程使用其他 RTOS 时，明确列出迁移到 FreeRTOS 的接口、时序和行为差异，并纳入框架审核；审核前保留原实现。新建工程也先给出裸机/RTOS 的依据和建议，由用户在框架阶段确认。

ESP 平台使用 ESP-IDF 时，采用对应 SDK 支持的 FreeRTOS 实现及其移植约定，不另行叠加一个不匹配内核。具体核心数、栈单位和同步方式按选定芯片及 SDK 版本核对。

## 5. WF06：例程、库与技能发现

优先分析用户提供的芯片例程和 lib/SDK。没有时上网寻找，优先厂商官方站点、官方代码仓库和器件支持包；记录下载来源、型号/封装、版本、工具链、依赖和许可。核对启动文件、中断向量、头文件、二进制库 ABI、存储模型及链接配置后才接入。

find-skills 用于寻找和核对专业能力，不能代替规格书、网表解析、规则检查器、编译器或调试工具。按阶段选择并记录：

| 阶段 | 能力组合 |
| --- | --- |
| 原理图分析 | find-skills 核对 EDA/原理图、PDF 和图像读取能力；原生嘉立创EDA文件可选择本机已有 easyeda-agent，其他格式按实际工具支持处理 |
| 框架规划 | find-skills、Superpowers 的需求澄清/方案与计划能力、embedded-systems、当前框架规则 |
| 规范复盘 | find-skills 选择静态分析、代码审查和测试能力，结合本工程规则检查器 |
| 逻辑与引脚复盘 | find-skills 选择嵌入式、EDA、协议和时序分析能力，逐项追溯到资料及代码 |
| 构建及错误处理 | find-skills 核对 IDE/编译器相关能力；Superpowers 的系统化调试和完成前验证用于处理失败与保留证据 |

已有且已核验的技能按相同适用条件复用，不为每个文件或每轮复盘重复搜索、安装。新增候选核对内容、来源、安装量、仓库维护和适用范围；低安装量候选不直接作为结论依据。搜索不可用时记录原因，继续使用已具备的能力，不伪造搜索或安装结果。

这些技能是执行方法，用户规则和已确认的工程方案决定实际范围。遇到工作流冲突时先遵循用户已经给出的授权与要求，不叠加重复确认步骤。

## 6. WF07：原理图与芯片底层交叉分析

原生 EDA 输入尽量读取器件、引脚和网络；PDF/图片输入同时读取页面文字和图面连接。仅 OCR 或网名匹配不能证明电气连通；无法辨识的跨页连接、交叉点、位号和引脚标记为待确认。

逐项建立以下证据链：

`原理图版本/页码/位号/网络 → 具体封装物理脚号 → MCU GPIO/复用功能 → 外围电路和电气方向 → HDL 配置/读写 → FML 能力 → APP 业务条件`。

检查供电和参考电压、输入/输出方向、复用资源、上拉/下拉、开漏/推挽、反相/隔离链、上电/复位默认态、启动绑带、调试接口，以及外设、定时器、IRQ/DMA 的资源冲突。电压、时钟、极性和保护条件必须有实际资料依据。

输出引脚功能表、引脚逻辑表和问题清单。软件“置1”是否表示负载使能，必须沿外围反相、驱动和隔离链核对，不能从 GPIO 名称直接推断。输入脚同时记录采样方式、有效电平和异常输入处理。

枚举所用封装的全部物理引脚；电源、地、NC、保留脚和未使用脚分别登记用途或限制。固件不参与的脚说明理由，不能把未识别网络当作 NC，也不能遗漏启动和调试复用脚。

## 7. WF08–WF09：完整 HTML 框架与逐步审核

在搭建 IDE 工程前，必须交付可打开的 HTML 程序框架审核包，并附关联图形。使用 find-skills、Superpowers 和本框架规则完成分析与方案组织。

HTML 必须包含：

1. 芯片、规格书、原理图、SDK、IDE/工具链、旧代码和分析范围的资料摘要及缺项。
2. 系统整体架构图、四层模块职责、依赖、接口、数据流和初始化顺序；重构时展示原框架与拟采用框架的差异。
3. 裸机分时任务表，或 FreeRTOS 任务/优先级/同步/资源表；中断、快路径和故障处理单独标示。
4. 引脚功能确认表：物理脚、GPIO/复用、网络/位号、方向、用途、资源与资料来源。
5. 引脚逻辑确认表：有效电平、反相链、上下拉、上电/复位/运行/故障状态、触发条件和软件动作。
6. 业务逻辑/状态转换图，以及需确认的信号时序或波形图；PWM、通信、片选、使能、复位等按实际项目选择，标明时间单位、边沿、极性和约束来源。
7. 分阶段的缩略审核表：先显示概要和待确认项，按阶段展开详细表格；图形提供缩略预览及放大查看。
8. 每项“待确认/已确认/需修改/不适用”的状态、用户意见、方案版本和对应证据，以及继续实施所需的确认项汇总。
9. UI工程附3–4套（默认4套）场景界面风格、相同内容的对比、交互/状态与资源限制，用户选择后纳入对应方案；详见[UI审核模板](../templates/embedded-ui-review-template.md)。

HTML 本地可打开，必要图形随包保存，关键内容不依赖联网才能阅读。MD 继续用于规则、分析和记录；HTML 是本次用户要求的框架审核交付物。

设计逻辑图和预期波形标为“设计预期/待确认”；仿真图注明模型、输入和条件；实测图注明仪器、采集条件和实际文件。没有测量数据时不能绘制并声称为实测。资料未定时展示待确认位置，不填入虚构引脚或时序数值。

审核分五步：资料/平台 → 系统框架 → 引脚功能 → 引脚逻辑与图形 → 实施范围。使用[审核表模板](../templates/embedded-project-review-tables.md)逐步确认，不以一次笼统的“看过了”覆盖未确认的具体冲突。

用户明确确认所列版本和范围后才能进入工程搭建。HTML 本地勾选若未实际取得用户回复，只是草稿状态。已确认内容不重复询问；后续更换芯片、修改引脚、调度方式或其他影响方案的变更，只更新并确认受影响项。

## 8. WF10：搭建对应 IDE 工程

审核确认后开始：

1. 使用已确认版本的 CCS、Keil 或 VS Code 配套工具链，导入经核对的官方例程或建立工程。
2. 配置芯片/封装、启动与向量、时钟、存储布局、链接文件、SDK/lib、调试器和构建组合。
3. 按已确认分支建立裸机分时框架或 FreeRTOS 框架，落实 Task/APP/FML/HDL、端口、初始化和模块生命周期。
4. 按已确认引脚表实现 GPIO/复用/外设，接入业务逻辑、错误恢复和必要的调试接口。
5. 保留工程构建方法、依赖版本、目标产物及输入摘要；重构在副本中实施，保持原工程可追溯。
6. 在工程根目录创建`Log/版本记录.md`、`Log/提示词记录.md`；已有内容保留。按[Log规范](embedded-log-rules.md)和[记录模板](../templates/embedded-project-log-template.md)逐次追加，每条空行分隔，后续改代码先检索相关记录再核对当前实现。

厂商 SDK/固定入口保留原契约，不为自有命名规则批量改写。工程搭建后的主流程是先完成下述两组复盘，再做第11节的正式验收构建；开发中的必要试编译可以进行，但不能替代两组复盘或最终构建。

## 9. WF11：每个文件的规范与规则三轮复盘

实现完成后，通过 find-skills 选择/复用适用能力，自动执行全部可执行规则检查，并对所有规则逐条分析和记录覆盖方式。每个纳入工程范围的文件都要有三轮复盘结果。

先冻结文件清单和 SHA-256，包括自有源码/头文件、实际参与构建的 SDK/第三方源码与头文件、启动与链接文件、配置和接入的库。每行记录文件类别；SDK/第三方三轮核对其代码适用性、集成、配置和契约，自有命名条款按既定范围标为不适用，不擅改供应商实现。预编译 lib 无源码时记录二进制摘要、ABI、公开接口及集成分析，内部实现标为源码不可得/未验证，不宣称已经完成内部源码复盘。

| 轮次 | 每个文件的重点 | 必须留下的证据 |
| --- | --- | --- |
| C1 形式和基础规则 | 编码、命名、声明、头文件、宏、表达式、注释、排版及实际适用规则 | 自动检查输出、规则编号、发现位置、不适用理由 |
| C2 语义和接口规则 | 职责、依赖、公开/私有边界、声明与调用、所有权、校验、错误、阻塞和重入契约 | 文件与接口分析、调用/依赖证据、发现和修复记录 |
| C3 组合和遗漏复核 | 回查 C1/C2 问题、相关构建组合、共享定义、SDK 例外、快路径及规则覆盖遗漏 | 复核结论、文件摘要、关联影响、未解决项和规则覆盖矩阵 |

三轮分别执行，不能复制同一份报告充当三轮。自动化覆盖不了的语义规则用具体代码证据分析；需要硬件证据的项目保留待测状态，不把工具未支持当作通过。检查器“0条发现”不等于所有规则均已验证。

文件缺轮次、摘要不匹配、适用规则漏项或存在未处理阻断问题时，不得写为完成。结果按文件记录，不能只给整个工程一个“三轮通过”标签。

## 10. WF12：全部逻辑和引脚功能三轮复盘

规范复盘后，再对全部业务逻辑和全部相关引脚功能执行三轮分析。每轮均覆盖逻辑与引脚，不能把一轮仅看代码、一轮仅看引脚当成两者都检查了三次。

| 轮次 | 逻辑与引脚交叉检查重点 | 证据 |
| --- | --- | --- |
| L1 正向追踪 | 从需求、规格书、原理图和已确认表追踪到任务、状态机、HDL 配置及输入输出；核对正常流程与预期波形 | 需求/信号/引脚到代码的映射及差异 |
| L2 反向追踪 | 从寄存器/SDK 调用、GPIO/复用、实际读写反查原理图网络和业务意图；检查方向、极性、复用、边界与异常路径 | 代码到资料的映射、反相链、冲突和失败路径记录 |
| L3 整体复核 | 重新覆盖全部逻辑与引脚，交叉核对上电、复位、运行、故障、超时、并发、实时调度、优化相关共享访问及图形一致性 | 问题关闭、仿真/测试/待测清单、当前版本与限制 |

每项逻辑和引脚有 L1/L2/L3 记录及代码/资料位置。软件分析、仿真和实测分别表述。没有样机、仪器或接线时完成可做的分析，明确硬件未验证，不虚报波形、时延或引脚实测。

修复引起文件、逻辑、引脚或构建配置变化时，更新摘要，对修改及受影响范围重新完成相关三轮；已有未受影响证据可复用。变更影响已确认方案时回到相应审核项，避免使用旧版本结论放行新产物。

## 11. WF13：IDE 编译、告警与优化器分析

两组复盘完成后，打开对应 IDE 并加载已确认目标工程，执行实际目标构建。可调用该 IDE/工具链匹配的官方构建接口，记录 IDE、编译器、构建配置、完整命令、退出码、日志及产物；不能用主机语法检查冒充 CCS/Keil/目标构建。

IDE 无法自动打开或操作时，记录实际限制和可用构建方式；需要用户手工操作的步骤明确列出，不声称已打开或已构建。未获得的目标编译结果保持未完成。

编译错误按“读取真实错误 → 定位根因 → 修复 → 复核受影响范围 → 重新构建”继续，直到 0 错误，或确实需要用户手工解除的问题才能停止。每轮修复有具体依据，不重复相同失败命令冒充进展。

确需手工处理时交付原始错误、原因、已尝试操作、影响范围和最小处理步骤，例如缺失的受许可工具链、IDE 对话框或不可自动处理的设备配置。此状态为“需手工处理/未完成”，不能作为成功交付。

告警逐条归类：影响类型/指针、初始化、越界、截断、未定义行为、链接/内存、ISR/共享数据或实际功能的告警需要处理；经分析与工程无关或无实质影响的既有告警可以忽略，但记录原文、理由、适用版本和范围，不通过全局关闭告警掩盖问题。

必须结合最终优化设置分析：

- 核对发布/实际烧录配置、ABI、LTO 和相关编译选项；Debug 成功不能替代实际发布配置。
- 检查未定义行为、别名/对齐、数值范围、浮点选项、硬件访问顺序、volatile 与同步，防止优化暴露潜在错误。
- 检查内联、直接/间接调用、函数/数据保留、链接段与 RAM 放置，必要时比较目标反汇编、MAP 和资源使用。
- 快路径按总规则验证调用和布局；WCET、抖动和外设波形仍须实机证据，静态分析不冒充时间测量。
- 修复编译/优化问题后更新相关复盘记录并再次构建，直至当前产物与通过审核/复核的输入一致。

最终软件状态是目标构建 0 错误、告警已处理或有依据地登记忽略、优化风险已处理或明确待验证，以及两组复盘对应当前输入。只满足其中一项不等于全部完成。

## 12. WF14：接线就绪后的自动烧录

适用本流程、方案已确认且用户已告知当前目标的烧录线接好时，按照用户本次规定，目标编译和软件检查完成后直接烧录当前已确认固件，不重复索取同一烧录许可。

执行前核对当前板卡/芯片、探针、目标电压、端口、固件摘要、链接地址/分区和已确认烧录范围。只检测到探针不能用来猜测连接的是哪块板；目标有歧义时先澄清目标。

遵守已确认擦写范围，保留范围外的 Boot、校准、参数和密钥区域；无法按范围执行或需要改变方案时，先说明具体差异。不能把普通烧录默认为整片擦除。

记录下载工具、目标、产物 SHA-256、写入结果、校验结果和运行方式。执行失败先定位，不能无限擦写重试。没有接线时保留已编译产物和待烧录状态；烧录成功不等于系统功能或实机波形验证通过。

## 13. WF15：调试信息与现场观察

用户连接调试口后，按已确认连接使用串口、SWO、JTAG/SWD 或厂商支持的实际观测方式；先核对接口能力、引脚和配置，不把任意 debug 连接都等同于 printf 通道。

可输出启动/复位原因、任务心跳、模块状态、错误码、关键计数和受控参数快照，结合实际需求观察运行。控制 ISR 不加入阻塞打印和格式化日志；使用缓冲、限频和前台输出，记录观测对实时性的影响。

日志注明时间、固件版本/摘要、目标和采集方式。根据反馈定位并修复问题；涉及源码、引脚、逻辑或编译配置变化时按第10、11节回到相关复盘和构建，接线就绪且范围未变时继续烧录验证。

无可用连接或未采到数据时标为待调试，不把仿真、示例日志或模型推断作为现场观测。

## 14. WF16：交付、追溯与规则来源

每个工程交付资料索引、确认过的 HTML/图形及审核版本、IDE 工程与源码、规则覆盖矩阵、逐文件 C1/C2/C3、逐逻辑/引脚 L1/L2/L3、问题关闭与例外、构建/告警/优化报告、产物摘要，以及实际存在的烧录和调试记录。缺失的硬件验证明确列出。

同时交付`Log/版本记录.md`和`Log/提示词记录.md`，保留全部追加历史，关联实际版本、修改文件、提问摘要与最终改善输出；不把工程维护记录混为芯片运行日志。

审核记录绑定资料版本、源文件/配置摘要和用户确认范围；修改后标识受影响项，不能让旧确认或旧检查继续证明新版本通过。
